# One YAML implementation sits behind every Format

A Format says how a Source's bytes are encoded, not what they mean, so the same authored scalar should read back as the same value whichever Format carries it. It did not. `md`/`mdx` frontmatter went through `gray-matter`, whose built-in engine is js-yaml — **YAML 1.1**, which has a `timestamp` type and so turns date-shaped scalars into JS `Date` objects. `.yaml` Sources went through the `yaml` package — **YAML 1.2 core**, which has no timestamp type and leaves them as strings. One `Format` union sat on two YAML specs, and `normalizeMetadata` was left holding a `Date` it had to turn back into text with no schema to consult and no sight of the original scalar. Its guess — `toISOString()`, sliced to `yyyy-mm-dd` when the instant landed exactly on `T00:00:00.000Z` — is what produced the damage: `2026-07-14T09:30:00` acquired a `Z` it was never written with ([#114](https://github.com/aureliushq/kobun/issues/114)), `2026-07-14T00:00:00.000Z` lost its time and then failed the validation it had passed ([#115](https://github.com/aureliushq/kobun/issues/115)), and `2026-07-14T09:30:00+05:30` was silently rewritten into a different spelling of the same instant. The guess was not improvable at that seam: `2026-07-14` and `2026-07-14T00:00:00Z` arrive as the *same* `Date`, and telling them apart needs source text that `normalizeMetadata`, being deliberately schema-free, neither has nor could act on. We removed the fork instead of the guess. `app/lib/yaml.ts` exports one `yamlCodec`; `app/lib/frontmatter.ts` registers it as gray-matter's `yaml` engine and the Content Document's `DATA_CODECS` uses the same object, so "one implementation" is a fact about the code rather than a claim about it, and a scalar means what it says.

## Consequences

- `normalizeMetadata` is deleted, along with its barrel export and its call sites in `parseDocument`/`asData`. No parser in the app emits a `Date` any more, so nothing downstream has to defend against one, and `app/core/content/normalize.ts` keeps only `canonicalMetadata`.
- A zoneless datetime is now **rejected in every Format**, which is what the `datetime` validator has always said it exists to do: without a zone the value names a different moment in every timezone. `hasExplicitZone` is unchanged — the fix was never in the validator.
- `md`/`mdx` frontmatter is YAML 1.2 core, so the YAML 1.1 spellings behave as they always have in `.yaml` Sources: `yes`/`no`/`on`/`off` are strings rather than booleans, `0644` is decimal `644` rather than octal `420`, and sexagesimals like `1:30` stay strings. `true`/`false` are unaffected in both specs. No occurrence of any of these exists in this repository.
- The codec normalizes CR and CRLF to LF before parsing — the step YAML 1.2 asks of a parser and the `yaml` package leaves to its caller. `gray-matter` cuts the frontmatter block out of a CRLF file by byte offset and hands the parser a dangling lone CR, which js-yaml tolerated. Refusing it is the better of the two things a strict parser does with one: where the CR lands on a plain scalar it is folded into the *value* instead, so `published: 2026-07-14` on a CRLF Source read back as `"2026-07-14\r"` and failed the `date` Field's validator. Normalizing closes both. Fidelity is untouched: unchanged Data is re-emitted from the Source's own bytes, and the Body is sliced off the raw string rather than off anything the parser returned.
- Serializing is now idempotent for date-shaped strings. js-yaml re-quoted `2026-07-14` to `'2026-07-14'` on the first Data edit, because unquoted it would have parsed back as a `Date`; the `yaml` package emits it bare and reads it back as the same string.
- [ADR-0002](./0002-content-document-fidelity-via-original-raw.md) is amended: its claim that `parseDocument` returns *normalized* Data no longer describes the module.

## Considered options

- **Make `normalizeMetadata` schema-aware** — let it see the Field Type and coerce a `Date` accordingly. Rejected: it breaks the module's deliberate schema-free split, leaves the two-spec divergence in place for every non-date value, and still cannot recover the zone the writer did or did not type.
- **Keep js-yaml, give it the core schema** — `js-yaml` is a transitive dependency of `gray-matter`, not one this repo declares; reaching past a dependency to configure its own dependency is a coupling that a `gray-matter` bump would break silently. The `yaml` package is already a direct dependency and already the authority for `.yaml` Sources.
- **Replace `gray-matter` outright** — the frontmatter split, the delimiter handling, and the `content`-is-a-literal-suffix property the fidelity slice depends on are all things it gets right. Only its choice of YAML engine was wrong, and that is the one part it lets a caller replace.
