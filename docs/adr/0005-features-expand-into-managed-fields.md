# A Feature expands into Managed Fields in the resolved schema

> **Amended.** As first accepted, this ADR made a Managed Field read-only in the editor and rejected "Injected *editable* Fields" outright. That reversed during #86: a Managed Field is **editable**, and the marker decides only where the properties panel puts the control, never whether there is one. The reasoning is recorded under Considered Options below, and the stamping rules were softened to match. Everything else here stands as accepted.

> **Amended again.** The **never-backfill rule for Publication State** below is superseded by [ADR-0008](./0008-commit-and-publish-are-separate-acts.md). It was a rule about *Sources* — never add `status` when absent, never overwrite it when present — because Publish was the only path to the repository and could not tell an ordinary edit from a declaration of intent. Now that **Save to GitHub** exists, it is a rule about *actions*: `status` is written by Publish and by nothing else, and Publish always writes `published`. Ordinary editing goes through Save to GitHub, which touches nothing, so the silent-unpublish this rule guarded against is closed by construction. The three timestamps are unchanged, except that `publishedAt` is written only by Publish.

`features` has sat in the Config schema since the first schema commit (`featureSchema`, `packages/config/schema.ts`) with no consumer: it validates, it rides into `NormalizedConfig` untouched, it is advertised to config authors through the published JSON Schema — and nothing in the app reads it. The exported `Features` type is imported nowhere; `featured` appears nowhere outside its own declaration. The behavior `features` names exists only as hardcoded frontmatter key-sniffing in the collection list, where `deriveStatus` guesses at `status`/`draft`/`published` and `deriveCreatedAt` guesses at `createdAt`/`date`/`publishedAt` (`app/routes/collection.tsx`), neither asking what the Collection declares even though the loader already holds it. We are making `features` real by deciding that a Feature expands into **Managed Fields** — ordinary Fields in the resolved schema, each carrying a marker saying the system stamps the value, which the writer may still correct. Expansion happens once, in the config layer, so the editor, the Data defaults and validation, the serializer, the viewer, and the list all see plain Fields and need no knowledge that Features exist.

| flag | contributes |
|---|---|
| `timestamps.createdAt` | `createdAt` — `datetime`, "Created" |
| `timestamps.updatedAt` | `updatedAt` — `datetime`, "Last updated" |
| `publish` | `publishedAt` — `datetime`, "Published" |
| `publish` | `status` — `draft`/`published`, "Status" |

`publishedAt` belongs to `publish` rather than to `timestamps` because it is not a fact about when bytes changed — it is a fact about publication, and it means nothing without a Publication State beside it. A Collection with `timestamps` and no `publish` has no notion of being published, so a `publishedAt` there would be either a synonym for the first `updatedAt` or permanently empty. The two flags also stamp on opposite rules — `updatedAt` advances on every publish the writer has not set it on, `publishedAt` is written once — so grouping them would file a write-once field under a flag whose other fields are write-always, and would let a config ask for a publication date without the state that gives it meaning.

Expansion is a step in `packages/config`, after per-entry validation, on the way to `NormalizedConfig` — not a per-consumer concern in the app, which would grow a parallel "and also the Feature fields" branch in five-plus places and drift, the way the config preamble drifted before the project-context seam and the field-type switches drifted before ADR-0004's registry. It would also leave the collision check with no particular home. The cost is paid at the config contract: the published JSON Schema is generated straight from `kobunConfigSchema` (`scripts/generate-schema.ts`, Zod's `z.toJSONSchema`, served from `/schemas/v1.json`), so expansion has to sit *outside* the Zod schema — otherwise authors would be prompted to write `createdAt` into their own `schema` block and then told off for colliding with it. **The published JSON Schema therefore describes the authored shape and never the resolved one.** Two shapes now live under one name and only the authored one is documented, so a reader of the JSON Schema cannot see the Fields a Collection will actually have. The corollary is that the managed marker is the config layer's own output rather than authored vocabulary, so a Config that writes the marker directly has it ignored.

A Collection that declares `createdAt` *and* enables `timestamps.createdAt` is a config error that names the key and points at the Feature. Both silent resolutions are wrong: let the declared Field win and the Feature quietly does nothing, or let the Feature win and the writer's Field — its type, its label, its options — quietly vanishes from the editor. Either way the config says one thing and the app does another. The error is scoped to that Collection, because `validateConfig` already validates each entry independently and collects errors per key (`packages/config/validator.ts`); one bad Collection must not blank a whole Config. `features` on a Singleton is likewise rejected, with an error saying it is not yet supported there. `featureSchema` hangs off `singletonSchema` as well and always has, but the singleton write path is a stub (`app/routes/singleton-editor.tsx` is `// TODO: implement`; `app/routes/singleton.tsx` is a read-only viewer with no action), so expanding there would mint Managed Fields empty by construction, forever — a Feature that looks enabled and does nothing. A loud error beats permanent silence, and the rejection lasts only as long as its reason does.

The three timestamps backfill onto Sources that predate the Feature — `publishedAt` included, despite belonging to `publish` — because each records a moment in the file's life that Kobun is present for: it is the thing changing the bytes, and the thing performing the publish. **Publication State never backfills.** `status: published` is written only for a Collection Item Kobun is creating; a pre-existing Source that lacks `status` never gains one, and a pre-existing Source that carries one keeps it byte-identical, whatever it says. The line is not timestamp-versus-not, it is what Kobun observes versus what it must be told: Publication State is the writer's intent, and the site owns what it means — including the convention that the key's absence is itself a state. Kobun forms no opinion about content it did not author, because there is no correct guess available, and guessing would let an ordinary typo fix silently unpublish a live post.

`createdAt` is stamped when a Draft is first minted, so a new Collection Item reads as Created and `draft` before it has ever been published. `updatedAt`, `publishedAt`, and `status` are stamped server-side at publish, and only when the content otherwise changed: `updatedAt` advances every time *unless the writer set it themselves*, `createdAt` and `publishedAt` are kept if already set, and `status` follows the never-backfill rule above rather than a timestamp's. A writer's edit is recognised by the value differing from the one the Source carries, so no dirty-tracking is needed and no stamp ever silently discards what the writer typed. `createdAt` has to go into the content rather than onto the Draft row because a Synced Draft is deleted — ADR-0001's publish chain is commit → guarded sync → delete-when-synced, so the row that would hold the creation time does not survive the publish that needs it. The value belongs where it survives, which is the Source's Data. That carries one ordering constraint: a publish whose content already matches its Source short-circuits into no commit, and the comparison includes Data, so a stamp applied *after* the Draft is persisted would leave a surviving Draft permanently disagreeing with its Source, the comparison never matching again, and every later publish committing a fresh timestamp forever. The stamp is applied before the Draft is persisted, gated on a comparison computed against unstamped values.

## Considered Options

- **Injected *editable* Fields** — Features contribute ordinary Fields with an editable control. Originally rejected on the grounds that the values are the system's, so an edited `updatedAt` would be overwritten at the next publish and an edited `status` would fight the never-guess rule, leaving a control that accepts typing and discards it. **Accepted on amendment.** The values are the system's *defaults*, not its property: backdating a `publishedAt` on an imported post, or flipping `status` back to `draft`, is ordinary writing work with no other way to do it, and forbidding it sends the writer to the repository to hand-edit frontmatter Kobun claims to own. The discard the rejection feared is a property of the stamping rules rather than of editability, and those rules were softened to preserve a deliberate edit — `createdAt`, `publishedAt` and `status` already kept an existing value, and `updatedAt` now does too when the writer set it. What survives the amendment is the *grouping*: a Managed Field is a fact about the item rather than something the writer set out to write, so it sits below a divider, last.
- **Read-only Managed Fields** — the original decision: static text, no control, the read-only branch checked before the Field Type dispatch. Rejected on amendment for the reasons above, and because it made the panel carry a second parallel field-type dispatch — a formatted datetime, an option label, an em dash for unset — which is exactly the drift ADR-0004 exists to kill, for four fields.
- **A separate metadata concept beside Data** — feature values in their own namespace outside the Content Document, with every consumer taught about both. Rejected: it duplicates the whole Field machinery — ADR-0004's five behaviors, default and validate and both renders and the edit control — for four fields, and the values have nowhere to live in the Source. They *are* frontmatter keys, indistinguishable from any other, which is exactly what the list's key-sniffing already assumed.
- **Widening `date` instead of adding a `datetime` Field Type** — give the existing day-only `date` a time component. Rejected: it changes how every existing `date` Field validates and renders, for a change no existing config asked for, while a day-only date stays a real thing writers want. A tenth Field Type is the honest answer, on the reasoning ADR-0004 used to refuse `FieldType.TITLE`: a value kind gets its own type rather than a costume worn by a neighbor.
- **App-layer per-consumer resolution** — leave `features` where it is and let each consumer read it. Rejected: the parallel-branch drift above, plus the collision check would land nowhere in particular, or in several places phrased differently.

## Consequences

- A live bug falls out with the work: `timestamps` is currently the only non-optional key of `featureSchema` while its own inner keys are optional, so `features: { publish: true }` fails validation today and the published JSON Schema advertises `required: ["timestamps"]`.
- The list's key-sniffing survives as the fallback for Collections that have not opted in, so a Collection with no Features behaves exactly as it does today. One narrowing comes with opting in: the sniffing recognizes a third state, `scheduled`, that a Feature-declared `status` does not offer — a Collection that wants it keeps the convention instead of the Feature until something widens the flag.
- The editor's properties panel gains a group below a divider holding the Managed Fields, rendered with their ordinary editable controls. The partition happens where the panel's field lists are already built (`getCollectionEditorFields`, `app/core/editor/collection-metadata.ts`), so the desktop panel and the mobile sheet stay one change rather than two, and a Collection with no Features renders neither divider nor group.
- **"Save to GitHub" is settled**, in [ADR-0008](./0008-commit-and-publish-are-separate-acts.md). The constraint recorded here — that until that action exists every file Kobun commits is published by construction — is discharged. It inherited the ordering constraint above and kept it: `status` became a clock-free intent stamp applied *before* the matches-Source comparison, while the timestamps stayed after it, so no clock ever enters the comparison and the churn bug stays closed.
- This constrains the **singleton editor**: building it removes the only reason for the singleton rejection, and the follow-up that lifts the rule records here that it has been lifted, rather than quietly contradicting this ADR.
- **`featured` stays inert.** `featured: { limit: number }` is a constraint across a whole Collection, not a fact about the item being edited, so it does not fit the expand-into-Fields shape settled here; enforcing a cap needs to know what the other items say. It gets its own grilling, and removing it from the Config schema is a valid outcome there.
