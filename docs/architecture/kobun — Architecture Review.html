Architecture Review · deepening opportunities

kobun

A Git-backed CMS: content lives as files in a GitHub repo, shaped by a config-driven schema of field types, edited through a Tiptap editor and a draft layer in D1. This review looks for shallow modules — where the interface is nearly as complex as what it hides — and proposes turning them deep, so the logic becomes testable and AI-navigable.

Where content flows today

Every content route reaches directly into low-level tools — octokit, gray-matter, YAML.parse, base64. There is no module that names "a content document" or "a draft's lifecycle". Those concepts exist only as inline code inside route loaders and actions.

Candidates

Candidate 01

The Draft is a lifecycle, not a table

Strong
app/routes/collection-editor.tsx L156–633 app/core/editor/drafts.ts (42 lines) db/schema/app-schema.ts · editorDraft

Problem

The genuinely hard concept in kobun — reconciling a D1 draft against the live GitHub file with optimistic concurrency — lives entirely inline in a route's loader and action. The action alone is ~220 lines juggling revision, publishedRevision, sourceSha, 409-conflict branches, draft rebase, post-publish sync and draft deletion.

Meanwhile drafts.ts — the file that looks like the draft module — holds only three one-line pure predicates (isDraftDirty, isPublishedDraftSynced, getDraftEditorPath). The real state machine has no home. The bugs hide in the calls, and the calls are only reachable through an HTTP POST.

Solution

Extract a deep Draft module (an EditorSession / working-copy store) that owns the transitions behind a small interface — openDraft, saveDraft, publishDraft — and hides all revision/sha bookkeeping. The route becomes a thin adapter: parse request → call one method → return JSON.

Benefits

  • Locality: every rule about "when does a draft become dirty / synced / deleted" sits in one file, next to the schema it guards.
  • The interface becomes the test surface: concurrency races (409s, stale sha, rebase) become plain unit tests instead of requiring a driven HTTP action + real GitHub.
  • Leverage: the stubbed singleton editor can reuse the exact same module instead of cloning 400 lines.

Candidate 02

Give "a Content Document" a home

Strong
singleton.tsx L119–135 collection.tsx L110–118 collection-items.server.ts api.repo-asset.ts L98–102

Problem

A repo file is really a content document: raw bytes ⇄ { frontmatter, body }, keyed by format (md, mdx, json, yaml). But that knowledge is scattered and asymmetric:

  • Parsing lives in 3+ places — singleton.tsx branches over all four formats inline; collection.tsx calls matter() inline; collection-items.server.ts does it properly (md only).
  • Serializing lives in exactly one place — and only for markdown. There is no json/yaml write path, and singletons have no write path at all.
  • base64 leaks: because getGithubFileContent returns atob output, api.repo-asset.ts hand-rebuilds bytes with a charCodeAt loop, coupling a route to the wrapper's encoding choice.

Solution

A single Content Document module: parseDocument(raw, format) → { data, body } and serializeDocument(doc, format, original?) → raw, absorbing the sourcePrefix "don't churn unchanged frontmatter" trick that today only collections enjoy. Add a bytes-safe read to the octokit wrapper so api.repo-asset stops decoding by hand.

Benefits

  • Locality: round-trip fidelity (parse then serialize = original) is one property test, not a per-route hope.
  • Leverage: the moment the singleton editor is un-stubbed, it inherits all four formats and churn-free writes for free.
  • Fewer format bugs: the "json/yaml can also carry a body?" question gets answered once.

Candidate 03

One way in: the authenticated repo context

Worth exploring
singleton.tsx · collection.tsx · collection-editor.tsx · api.repo-asset.ts config/github.server.ts · fetchAndParseConfig

Problem

Every content route opens with the same ~30-line ritual: getAuth → getSession → redirect if anon → find the project by owner/name → pull installationId → fetchAndParseConfig → dig the collection/singleton out of config. collection-editor.tsx already extracted this privately as resolveCollectionContext — one adapter is a hypothetical seam; four copies make it a real one.

There's a second smell nested inside: fetchAndParseConfig hits GitHub and re-validates on every navigation, while syncProjectConfig writes a cached configData blob to D1 that no content route ever reads back. Two representations of config, and the hot path uses the slow one.

Solution

Promote resolveCollectionContext to a shared RepoContext seam — requireRepoContext(args) → { session, project, installationId, config, env, db } — and let it own the config cache decision (read configData, fall back to fetch). Routes call it once and get everything typed.

Benefits

  • Leverage: auth + ownership + config resolution is touched by literally every route — fixing it once fixes it everywhere.
  • Locality: the "does this user own this repo?" security check stops being copy-pasted (it already drifted — api.repo-asset phrases it differently).
  • A single place to finally use the D1 config cache and cut a GitHub round-trip off every page load.

Candidate 04

The field type, defined once

Speculative
config/schema.ts singleton.tsx · FieldValue switch collection-metadata-fields.tsx · Control switch collection-metadata.ts · default + validate

Problem

kobun's core vocabulary is its field types — text, slug, url, date, boolean, image, select, multi‑select, array, object, document. Each type's behaviour is spread across five parallel switch statements in four files: the Zod shape, the default value, the validator, the read renderer, and the edit control. Adding "color" means finding and updating all five — and the compiler forces none of them to stay in sync.

Solution

A field-type registry keyed by type, each entry bundling { schema, defaultValue, validate, renderValue, renderControl }. The switches collapse into one lookup; a new field type is one entry the type system can force to be complete.

Benefits

  • Locality: everything about date reads top-to-bottom in one place instead of across four files.
  • AI-navigability: "how does image work?" becomes one grep, not a scavenger hunt.
Caveat — why only Speculative: read-render, edit-render and validate genuinely differ, and recursion (array/object nest fields) makes a clean registry interface non-trivial. Large blast radius across the two most complex files. Best attempted after 01/02 prove the extraction rhythm.

Top recommendation

01

Start with the Draft lifecycle module.

It is the deepest hidden complexity in the codebase and the one that most resists testing today — the concurrency logic is only reachable by driving an HTTP action against live GitHub and D1. Extracting it turns races and 409s into ordinary unit tests, and it directly unblocks the stubbed singleton editor, which would otherwise clone 400 lines.

Sequence

Do 02 (Content Document) first or alongside — the Draft module reads/writes through it. Then 01. Leave 03 and 04 until the rhythm is proven.

Payoff

The interface (openDraft/saveDraft/publishDraft) becomes the test surface; collection-editor.tsx shrinks from ~920 lines toward a thin route.

Risk

Contained — the extraction is behavior-preserving and covered by the tests it enables. No public API or config format changes.
